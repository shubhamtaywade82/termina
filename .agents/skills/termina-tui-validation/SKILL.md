# Termina TUI Validation

A TUI is not verified because TypeScript compiles or a snapshot passes. Validate the **rendered terminal experience and the state transitions behind it**. Choose the smallest test that catches the defect, then run broader checks for cross-package changes.

## Discover existing test and preview infrastructure

- Core tests live in `packages/core/test/`; the UI component tests live in `packages/ui/test/`.
- UI tests use the local renderer helper in `packages/ui/test/helpers/render.tsx`, built on the actual Termina renderer. It can expose frames and simulate piped stdin; mouse mode needs the appropriate TTY configuration.
- Core has an xterm-backed terminal fixture at `packages/core/test/helpers/xterm-terminal.ts` for physical row/cell and reflow-sensitive behavior. Use it for bugs that cannot be represented faithfully by comparing strings alone.
- Docs previews are generated by `examples/docs-previews/`, with generators and checks exposed through root scripts. Component live demos live under `docs-site/.vitepress/theme/demos/` and are wired into pages under `docs-site/ui/`.
- Follow existing `node:test` + `tsx` conventions. The core suite runs with concurrency set to 1; do not parallelize it casually.

## Validation workflow

1. **Define acceptance criteria first.** State the intended output, expected key/mouse actions, supported terminal conditions, important state transitions, and unacceptable failures.
2. **Choose representative dimensions.** Include a compact viewport (for example, 40×12), a common viewport (80×24), and a wide viewport (120×40) when responsive behavior matters. These are test scenarios, not guarantees that every terminal supports those exact sizes.
3. **Add a focused regression test.** Reproduce the failure before changing implementation when practical. Keep expected interaction/output assertions independent from the algorithm under test.
4. **Exercise real input.** Test key sequences for selection, submission, Escape/cancel, focus change, and navigation boundaries. For mouse behavior, enable the test harness's TTY/mouse path and assert hit-testing/callback behavior.
5. **Inspect physical layout.** Test clipping, wrapping, scroll offsets, cursor placement, and reflow when those are part of the bug. Use xterm-backed cells/rows when output width and physical terminal rows matter.
6. **Test alternate environments.** Cover monochrome/limited color, `TERM=dumb`, CI/non-TTY stdout, and piped stdin as relevant. Verify interactive control sequences are not leaked into ordinary logs.
7. **Check lifecycle and async behavior.** Assert listeners/timers are removed; completion and cancellation are distinct; loading stops on terminal outcomes; old responses cannot overwrite new state.
8. **Verify docs artifacts.** When public APIs or components change, update relevant docs and demos and run preview/documentation checks.
9. **Run broad checks and report evidence.** Separate what passed, failed, and was not run.

## Quality dimensions

### Visual and textual output

- Assert meaningful content, hierarchy, alignment, borders, truncation/wrapping behavior, and status labels—not only whether a substring exists.
- Normalize ANSI codes only when the assertion is about content rather than style. Keep tests that intentionally verify style/control sequences separate.
- Test wide/combining Unicode content whenever manual width calculation changes. Prefer established width utilities over ad-hoc string length.
- Include long labels, missing values, no results, one row, many rows, and content larger than the viewport where relevant.
- Ensure color is not the only distinction between selected, successful, warning, and failed states.

### Interaction

- Assert resulting state and callback data after each action, including boundaries and invalid actions.
- Check that only the intended component reacts to a key when multiple interactive components are present.
- Test component deactivation and focus movement; verify hidden components don't keep consuming input.
- For inputs, cover cursor positions, deletion, pasted control characters, and boundary editing relevant to the component.
- For scrolling/logs, verify clamping, tail-follow, manual scroll-away, return-to-tail, and data shrinkage.
- For asynchronous flows, test success, empty result, error, cancellation, retry, and duplicate input as relevant.

### Runtime behavior

- In core tests, cover mode entry/exit and cleanup across mount, unmount, suspension, exit, and failure as applicable.
- Do not claim resize/reflow correctness from a fixed-width string mock if the bug depends on terminal physical rows.
- Distinguish expected final-frame output from interactive rerenders and static output.
- Verify public API types and exports in addition to source-level behavior.

## Commands

Run targeted checks first:

```sh
pnpm --filter @nemesis-oss/termina-core run test
pnpm --filter @nemesis-oss/termina-core run typecheck
pnpm --filter @nemesis-oss/termina-ui run test
pnpm --filter @nemesis-oss/termina-ui run typecheck
```

Then run broader repository checks when practical:

```sh
pnpm run build
pnpm run typecheck
pnpm run test
pnpm run docs:previews:check
pnpm run docs:build
pnpm run verify
```

The root `verify` script builds, typechecks, and tests the workspace packages and examples. The CI script also performs frozen-lockfile installation, docs preview checks, and a production dependency audit; use the repository's documented CI process where full confidence is required.

## Evidence report

Report:
- The viewport sizes and environment modes exercised.
- The tests and commands actually run, with outcomes.
- Any manual/demo checks performed and what they proved.
- Remaining coverage gaps or unsupported terminal behavior.

Never claim a visual or end-to-end check passed if only typechecking or source review was performed.

## Handoffs

- Use `termina-tui-design` to define UX acceptance criteria.
- Use `termina-tui-app-architecture` or `termina-agentic-ui-patterns` to identify the state transitions and async cases that need testing.
- Use `termina-ui` for component-level regression tests; use `termina-core` for renderer and terminal protocol defects.
